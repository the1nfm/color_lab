# Сопроводительная документация: архитектура и соответствие заданию

## Схема

React UI → ограниченный пул module Web Workers → wasm-bindgen → ручной Rust parser → JS callback(offset, length) → File.slice → Uint8Array → Rust.

Rust экспортирует async inspect(size, read) и возвращает JSON. Callback — только диапазонное чтение сырых байтов. Браузерные Image, canvas, createImageBitmap, System.Drawing, PIL и специализированные библиотеки извлечения метаданных не используются.

Зависимости Rust:
- wasm-bindgen: JS/WASM ABI, экспорт функции;
- wasm-bindgen-futures: Promise/Future;
- js-sys: Function, Promise, Uint8Array;
- serde и serde_json: сериализация результата.

Ни одна из этих библиотек не определяет геометрию, DPI или глубину изображения. Все поля извлекает написанный здесь парсер.

В браузере нельзя напрямую вызвать обычный FileStream по произвольному Windows пути. Аналог: пользователь разрешает доступ к File/DirectoryHandle, диапазоны файла читаются через стандартный File.slice().arrayBuffer(). Это соответствует «FileStream (или аналог)», но такое трактование стоит согласовать с преподавателем.

## Планирование и асинхронность

Папка сначала перечисляется без чтения содержимого картинок. Для File System Access API обход итеративный, асинхронный, с накоплением до 100000 File ссылок. При превышении лимита обработка не начинается. input webkitdirectory формирует список на стороне браузера, поэтому его первоначальную работу контролировать нельзя.

Каждый Worker получает пачку до 16 файлов, последовательно обрабатывает её и отдаёт результат. Главный поток назначает следующую пачку освободившемуся Worker. Количество Workers ограничено 1–8. Не создаётся 100000 Promise/Workers одновременно. Один Worker имеет собственный экземпляр WASM, поэтому SharedArrayBuffer и cross-origin isolation не требуются.

Чтение в Worker асинхронное; парсинг Rust выполняется вне UI-потока. При остановке Workers уничтожаются, token защищает от запоздалых результатов. Снимок результатов обновляется примерно раз в 150 мс. Таблица рисует только видимые строки с запасом, а не 100000 DOM-элементов. Полный массив результатов и File ссылки остаются в памяти: это не O(1) RAM. Фильтрация и CSV выполняются на главном потоке и на очень большой выборке могут дать кратковременную задержку; это известное ограничение.

## Поточное / диапазонное чтение

Callback кэширует одну область обычно 64 КиБ на Worker/файл. Rust сначала проверяет границы и запрашивает только нужные байты. Крупный неизвестный TIFF-тег не считывается, но его размер/смещение проверяется. Содержимое PNG IDAT и TIFF полос/плиток пропускается. JPEG читается до SOS, затем проверяется хвост до 64 КиБ. GIF проходят по длинам подблоков без LZW-декодирования. PCX считывает заголовок и при необходимости маркер палитры.

Маленький файл может целиком оказаться в 64-КиБ окне; это не означает загрузку целиком многомегабайтных файлов. Максимальный единичный запрос служебных данных — 1 МиБ. При перемещении окна суммарное прочитанное число байтов может превосходить размер файла из-за повторного чтения пересекающихся диапазонов.

Лимиты обхода защищают от зависания: до 200000 PNG/GIF блоков, 100000 JPEG маркеров, 256 TIFF IFD, 4096 тегов на IFD, 1 МиБ содержимого одного нужного TIFF-тега. Файлы, превышающие некоторые лимиты, могут быть корректными, но эта реализация не претендует на поддержку таких случаев.

## Статусы

- Структура OK: пройдены реализованные проверки; это не полная сертификация/декодирование.
- Файл повреждён: неверные заголовки, границы, обязательные маркеры, CRC служебных PNG-чанков; также ошибка чтения (подробность укажет причину).
- Не поддерживается: неизвестный формат, BigTIFF, неподдержанный вариант DIB или TIFF. Не следует считать такой статус доказательством повреждения.
- Замечание при структуре OK: например, сигнатура не совпадает с расширением или лишние данные после конечного маркера.

Если парсер завершается ошибкой, уже найденные поля не сохраняются: строка содержит имя, статус и текст ошибки. Следующий файл обрабатывается независимо.

## Что проверяется и чего не обещаем

PNG: полная сигнатура, IHDR первым, допустимые bit depth/color type, длины всех чанков, CRC IHDR/pHYs/PLTE/IEND, наличие IDAT и IEND, базовая проверка палитры. CRC IDAT, неизвестных чанков и zlib-данные не проверяются. Некоторые ограничения порядка ancillary/IDAT чанков также не проверяются.

JPEG: сегменты до первого SOS, SOF/SOS, JFIF/EXIF, ограниченная проверка EOI в последних 64 КиБ после SOS. Entropy stream не сканируется и не декодируется; внутренние сканы progressive JPEG не проверяются. JPEG с более чем 64 КиБ добавочных данных после EOI может ошибочно получить статус повреждения; это сознательное ограничение быстрого режима. JPEG DNL с отложенной высотой, hierarchical/нестандартные формы не гарантируются.

GIF: логический экран, таблицы цветов, размеры кадров, цепочки подблоков, наличие кадров и trailer. LZW-коды не декодируются; их внутренняя порча может не обнаружиться.

BMP: bfSize, DIB, геометрия, плоскости, bpp, сжатие, границы палитры/масок, размер пикселей для BI_RGB/BI_BITFIELDS и biSizeImage для сжатых. Содержимое RLE/embedded JPEG/PNG и действительность масок не декодируются.

TIFF: endian, classic magic 42, IFD chains без циклов, тип/число/inline или offset полей нужных тегов, RATIONAL, границы полос/плиток каждой страницы. Свойства отображаются для первого IFD. SubIFD/EXIF-подIFD, BigTIFF и old-style JPEG без обычных strip/tile тегов не поддерживаются. Сжатые пиксели не проверяются. Дополнительные IFD проверяются на границы, но не все их semantic constraints.

PCX: 128-байтный заголовок, версия, encoding, bits/plane, geometry, planes, BytesPerLine, присутствие палитры для version 5 8-bit indexed, грубая нижняя граница объёма. RLE-коды не проходят полный разбор, поэтому некоторые обрезанные PCX могут пройти. DPI берётся из заголовка, однако старые программы трактовали эти поля неодинаково.

Следовательно, проект демонстрирует ручной парсинг, Workers, range reading и обработку типичных битых файлов, но не гарантирует высший балл и обнаружение любого повреждения. Для полной валидации придётся потоково читать сжатые данные/CRC и при необходимости реализовать декодеры, что конфликтует с требованием всегда ограничиваться заголовками. Следует обсуждать с преподавателем, какой уровень проверки ожидается.
